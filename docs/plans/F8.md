## What the user gets

A fresh install holds the dock awake from its first launch while docked. The "Keep Dock Awake" item in the menu starts checked. Nothing else changes: unchecking it still releases the hold within five seconds and still survives relaunch (FR5), and the hold still follows the dock exactly (toggle on **and** dock present, the F3 rule). An owner who has already set the toggle, either way, keeps that setting.

Why: the series in `docs/learnings/keep-awake-experiment.md`. Off runs lost the dock's USB 3 side 4 times in 5 (at cycle 60, 52, 3 and 44); on runs held 66.2 hours with no sleep cycle and no loss. The owner's reaction to the second loss was that this is what the app is for (D36). D10, which set the default off, was never ratified; D36 supersedes it.

## Design

One decision, in one place, tested offline, with the app reading it rather than restating it.

- **`HoldPolicy.defaultToggle`** (DockCore, pure): a `public static let defaultToggle = true`, and `HoldPolicy.init` takes `toggle: Bool = HoldPolicy.defaultToggle`. The reducer itself does not change: hold exactly when the toggle is on and the dock is present, re-apply on wake. A fresh policy with no stored preference now holds the moment the dock arrives; that is the whole behaviour change, and it is one line.
- **Absent is not off.** `UserDefaults.bool(forKey:)` returns `false` for a key that was never written, which is how a flipped default would be lost. `AppDelegate` reads `object(forKey: keepAwakeKey) as? Bool` and falls back to `HoldPolicy.defaultToggle` only when the key is absent. A stored `true` stays `true`; a stored `false` (the owner unchecked it) stays `false`. The owner's installed copy has `keepDockAwake = 1` stored, so it sees no change.
- **The toggle still persists on every change** as it does now (`UserDefaults.set` in `toggleKeepAwake`), so after the first click the stored value, not the default, is what the app reads.
- **The `app.launch` line (D37) is the evidence.** Its `toggle` detail already reports what the app resolved at start, so a fresh install's first launch shows `toggle=on` in the log without any new logging.
- No change to `AssertionController`, `StatusItemController`, the menu wording, or the log kinds. `DockCore` stays free of AppKit (NFR7); nothing polls (NFR2).

Not in scope: RR1 (a lid-shut Mac on battery with no display still sleeps; unchanged by the default), a schedule window (D12, parked to v1.5 as its own delta), Launch at Login as a default (waits for D30). The default makes the hold the app's resting state while docked, so RR2 (a docked Mac held awake around the clock) becomes the expected condition rather than an opt-in; its mitigation row is updated to say the toggle is the way out and D12 is the planned refinement.

### F8-T2 — The app reads the default only when nothing is stored

Owner: agent · Delivers D36 · Checkpoint: with the debug binary (defaults domain `DockWatch`, log in `~/Library/Logs/DockWatch/`):

1. `defaults delete DockWatch keepDockAwake` (absent) → launch → `app.launch … toggle=on`, then `hold.on` while docked, assertion listed by `pmset -g assertions`; the menu item is checked.
2. `defaults write DockWatch keepDockAwake -bool false` → launch → `toggle=off`, no `hold.on`, no assertion.
3. `defaults write DockWatch keepDockAwake -bool true` → launch → `toggle=on`, `hold.on`.
4. From state 1, uncheck the item, quit, relaunch → `toggle=off` (the choice survived; FR5 persistence unchanged).

The installed instance (pid 27609, domain `com.martingleason.dockwatch`) is never launched, quit, or read from during these checks.
