# F6 — Eject dock volumes

Created: 2026-10-18 12:05 -05:00 · Edited: 2026-10-18 13:58 -05:00

**Status:** in progress (gate crossed 2026-10-18, "you can begin f6") · **Milestone:** MVP · **Owner:** agent · **Delivers:** FR9 (added by D11)

Order per D19: after F3, before F5 and F4. Learning level 5% (D6); every task is `owner: agent`.

## What the user gets

Every mounted volume on a disk that hangs off the dock appears in the menu with an Eject item, plus one "Eject all dock volumes". Each eject either happens or the menu says what blocked it ("Backups: in use by backupd"). Pulling the dock's cable after "Eject all" succeeds is then safe for the drives.

## What it cannot do, said plainly

macOS has no API to "eject" a keyboard, a receiver, a tracker or any device without storage. For those, "remove" is what the log already records: the device is gone and the menu no longer lists it. The menu never offers an action it cannot perform (CLAUDE.md non-negotiable).

## Design

- `VolumeEjector` (DockCore, DiskArbitration): `DADiskUnmount` with `kDADiskUnmountOptionDefault` (never force); the completion's `DADissenter` status is read as busy in both its spellings (`kDAReturnBusy`, or the kernel's `EBUSY` as a Mach error, which is what an open file produces), and the processes holding files on the volume are named through `proc_listpidspath` + `proc_name` (libproc, public). DiskArbitration exposes no dissenter PID publicly, so the plan's `proc_name`-on-the-dissenter idea became a volume-wide lookup. Result type `EjectResult { done | blocked(by: [String]) | failed(status, message) }`.
- "On the dock" classification (DockCore, pure, tested): a disk is on the dock when the IOUSB location ID of its USB device shares the controller byte (`locationID >> 24`) with the dock device's location. On this Mac the dock is `0x02148000` and its drives enumerate under the same `AppleT6000USBXHCI@02000000`; the built-in ports are controllers 0 and 1. The locations come from the disk's `DADiskDescriptionDevicePathKey` / IOMedia parent chain, read by `VolumeMonitor` (F2) and stored on the `volume.mounted` event, so F6 depends on F2.
- Eject section of the status menu (DockWatch): a "Dock Volumes" header, "Eject All Dock Volumes" when there is more than one, one "Eject “name”" row per volume, rebuilt in `menuNeedsUpdate` on every open (no timer, NFR2). A result stays beside its volume as the row's subtitle for 60 seconds and goes to the log as a `volume.eject` line with `result` and `done`.

## Design changes after the gate

Listed here rather than edited into the design above (F6 review, finding 9):

1. `blocked(by:)` carries a list of process names found by `proc_listpidspath` over the volume, not one name from a dissenter PID: DiskArbitration exposes no dissenter PID publicly. Root processes cannot be listed by a non-root app (RR13).
2. The eject UI is a section of the one status menu (header, Eject All, one row per volume), not a separate `EjectMenu`.
3. A result stays for 60 seconds, not 10, and after the review a just-ejected volume keeps a greyed row for that time so the result can be read; a remount clears it (`EjectMenuModel`, M10, M11).
4. "Eject" is an unmount, not Finder's whole-disk eject (D23).
