# F3 — Keep the dock awake

Created: 2026-10-18 10:55 -05:00 · Edited: 2026-10-19 08:48 -05:00

**Status:** in progress (gate crossed 2026-10-18, "begin work on f3") · **Milestone:** MVP · **Owner:** agent · **Delivers:** FR5, and the third state of FR1

Learning level 5% (D6); every task is `owner: agent`.

## What the user gets

A "Keep dock awake" item in the menu. While it is checked and the dock is plugged in, the Mac does not idle-sleep, so the power-delivery loop that drops devices never starts. The display still sleeps. Pull the dock and the hold is gone within five seconds; the Mac behaves exactly as before.

## Design

- `HoldPolicy` (DockCore, pure): a function `(toggle: Bool, docked: Bool) -> Bool` plus a tiny reducer over the inputs `toggleChanged`, `dockChanged`, `didWake`. It owns no IOKit. Every branch is tested (M1, M2, M6).
- `AssertionController` (DockCore, IOPMLib): creates `kIOPMAssertionTypePreventUserIdleSystemSleep` named `"DockWatch: keeping the Thunderbolt dock awake"` with `IOPMAssertionCreateWithName`, releases with `IOPMAssertionRelease`. Idempotent: `set(held: Bool)`. This type leaves display sleep untouched and dies with the process, which is why it was chosen over `pmset` or a `PreventSystemSleep` assertion (D3).
- Re-evaluation on `system.wake` from F2's `SleepMonitor` (NFR8; dark wakes are not observable, D18): macOS may release assertions across some sleep transitions; the controller re-applies the policy's answer on every wake.
- Persistence: the toggle lives in `UserDefaults` under `keepDockAwake`; default **off** (D10).
- `StatusItemController` gains the third icon state (held) from `AssertionController.isHeld`.

## Policy for RR14, decided at the gate

The hold follows `DockTracker` exactly: the identifying device gone means the hold is released within the five seconds FR5 promises, and its return re-asserts. No grace period. Reason: idle sleep requires the Mac to be idle for at least its one-minute `sleep` setting, so a flicker of seconds cannot start the dark-wake loop, while a grace period would be a second clock to get wrong. The `hold.off`/`hold.on` log lines (D21) make any such flicker visible after the fact.

## Risks touched

RR1 (an idle-sleep assertion does not stop lid-close sleep on battery without an external display, nor an explicit Sleep command; the menu wording says "idle sleep"), RR2 (a Mac held awake around the clock), RR4 (the hypothesis could be wrong; the evidence row above is the test).

**Two things learned building it.** A bare `swift build` binary reads `UserDefaults` from a domain named after the process (`DockWatch`), while the bundle from F5 will read `com.martingleason.dockwatch`; the menu toggle works either way, but anyone scripting the toggle should know which. And `applicationWillTerminate` does not run on SIGTERM for a bare binary, so the `hold.off` line is written only on a menu Quit; the assertion itself dies with the process regardless.
